# 패킷 유실 5% — 평균은 무사하고 꼬리만 죽는다 포스트모템

> 일시: 2026-07-23 00:18~00:22 (UTC) · 훈련 번호: 5 (roadmap 8장, 심화) · 장애는 의도적으로 주입됨

## 요약

Nginx 컨테이너의 egress에 5% 확률 패킷 드랍을 주입하고 같은 300rps 부하를 걸었다. **중앙값은 3.0ms로 미동도 없었지만 p95는 5.0ms → 240.6ms(48배), 최대는 1.7초**가 됐다. 커널 재전송 카운터(`TcpRetransSegs`)는 0 → 47. 실패율은 0% — 아무것도 "실패"하지 않았지만, 유실을 맞은 소수의 요청이 TCP 재전송 타임아웃(RTO)을 고스란히 꼬리 지연으로 떠안았다.

## 영향 범위

18,001 요청 전수 성공(실패 0%) — 그러나 상위 5%가 SLA(p99<200ms)를 위반. 지연 민감 서비스라면 "장애 없음"으로 보이는 채 사용자 경험만 나빠지는 유형.

## 근본 원인

- 5% 유실 → 해당 패킷은 TCP 재전송으로 복구되지만, 재전송 대기(RTO 최소 ~200ms, 지수 증가)가 그 요청의 응답시간에 그대로 더해진다. p95 240ms ≈ RTO 1회, max 1.7s ≈ 연속 유실로 RTO 백오프 누적.
- **분포 관점이 핵심**: 95%는 무사하므로 평균·중앙값 모니터링으로는 감지 불가. 백분위(p95/p99) 지표와 재전송 카운터가 있어야 보인다.
- 도구 제약의 기록: 교과서의 `tc qdisc netem`은 WSL2 기본 커널에서 불가 — netns 공유 사이드카(`--net container: --cap-add NET_ADMIN`) + `iptables statistic` 모듈로 동일 효과를 얻었다. 환경이 도구를 결정한다.

## 배운 점

- 패킷 유실은 실패율이 아니라 **꼬리 분포의 장애**다 — med 3.0ms가 유지된 채 p95만 48배가 됐다.
- 재전송은 "보이지 않는 재시도"다: 애플리케이션 로그 0줄, k6 실패 0건 — 증거는 커널 카운터(+47)에만 있었다.
- 주입 도구조차 환경 검증이 먼저다: netem 없는 커널에서 대안(iptables statistic)으로 우회한 과정 자체가 이 훈련의 절반이었다.
